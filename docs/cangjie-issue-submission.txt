字段 3  问题描述 Bug Description

现象
1. 在上述 Windows 补丁级别下，任何仓颉编译出的原生 exe 启动即崩：无任何输出，
   退出码为 -1073741819，即 0xC0000005 访问违例。
2. 用探针确认崩溃发生在 main 之前，属于运行时初始化阶段：main 的第一行就写文件，
   实测该文件从未生成。println 的输出为空只是因为 stdout 带缓冲，崩溃时未 flush，
   不能据此判断 main 是否执行。
3. 长驻服务同样起不来：调用 serve 后端口未监听，HTTP 请求无法连接。

崩溃签名，取自 Windows 事件日志 Application Error，多个不同程序完全一致
Faulting module name: msvcrt.dll, version: 7.0.26100.9444
Exception code: 0xc0000005
Fault offset: 0x0000000000062f1e
Faulting module path: C:\WINDOWS\System32\msvcrt.dll

自行解析 msvcrt.dll 的 PE 导出表后，该偏移落在导出函数 wcslen 内：
导出起始 RVA 为 0x62ED0，函数内偏移 0x4E，下一个导出 wcsncat 在 0x62FF0。
而 libcangjie-runtime.dll 与 libboundscheck.dll 都从 msvcrt 导入 wcslen。

一个反常点
WinSxS 中同时保留更新前后两份 msvcrt.dll，逐字节对比 wcslen 的结果是：
更新前 7.0.26100.8875 与更新后 7.0.26100.9444 的 wcslen RVA 同为 0x62ED0，
对比 288 字节完全相同，没有一个字节差异。
也就是说，崩溃点所在代码一字未改，且在更新前是可用的。

受控 A/B 对照
同一台机器，同一套仓颉 1.1.3，同一份 msvcrt.dll，仅卸载 KB5124010 并重启：
1. 最小程序：故障时崩溃且无输出，卸载后退出码 0 且正常输出。
2. 我们项目的可执行文件，约 3900 行仓颉：故障时 main 未执行，卸载后单测 197 项全绿。
3. 真实 HTTP 冒烟测试：故障时服务起不来，卸载后 220 项全绿。

已收窄到 ntdll
卸载前后逐项对比崩溃进程加载的系统 DLL，只有 ntdll.dll 发生变化，
即 10.0.26100.9539 变为 10.0.26100.9278，msvcrt、ucrtbase、msvcp_win、KERNEL32、
KERNELBASE 全部未变。因此我们判断问题很可能位于 ntdll，即 Windows 加载器，
与该版本仓颉运行时的启动路径之间，而不是 msvcrt 本身。

已排除的可能
1. 与本项目代码无关：空的最小程序同样崩溃。
2. 与 SDK 版本无关：1.1.3 与 1.0.5 都崩溃，各自配套的运行时 DLL 都试过。
3. 与环境变量、PATH、工作目录无关：使用全新默认环境、清空 CANGJIE_HOME、清空 PATH、
   极短路径、全新临时目录，全部崩溃。
4. 无第三方 DLL 注入：WER 报告的已加载模块列表里只有系统 DLL 与仓颉运行时，
   AppInit_DLLs 为空。
5. 无兼容性 shim：HKCU 与 HKLM 的 AppCompatFlags 下的 Layers 中没有针对这些程序的条目。
6. msvcrt 是 KnownDLL，在程序同目录放置同名 DLL 无效；把运行时目录全部 51 个 DLL
   复制到程序同目录也无效。


字段 4  复现步骤 Reproduction Steps

1. 准备环境：Windows 11 build 26300.9539，已安装 2026-09 预览更新 KB5124010，
   以及 Cangjie 1.1.3 cjnative，Target 为 x86_64-w64-mingw32。

2. 新建 repro.cj，内容见第 6 块。要点是在 main 的第一行写文件，而不是只打印。

3. 编译。请确保 CANGJIE_HOME 与所用的 cjc 来自同一个 SDK，否则会先撞上另一个
   前端与后端 LLVM 版本不一致的编译期崩溃，与本问题无关。

   $env:CANGJIE_HOME = "D:\Cangjie"
   $env:PATH = "D:\Cangjie\bin;D:\Cangjie\third_party\llvm\bin;" + $env:PATH
   & "D:\Cangjie\bin\cjc.exe" repro.cj -o repro.exe

4. 运行并观察。

   .\repro.exe
   "exit = $LASTEXITCODE"
   Test-Path .\marker.txt

   故障环境下的实际结果：程序无任何输出，退出码为 -1073741819，marker.txt 未生成。

5. 查看崩溃签名。

   Get-WinEvent -FilterHashtable @{LogName='Application'; ProviderName='Application Error'} -MaxEvents 3

   可见故障模块恒为 msvcrt.dll，偏移恒为 0x62f1e。

6. 可选对照：卸载 KB5124010 并重启后重复第 4 步，程序正常运行。
   建议随后恢复该更新再复现一次，以确认可重复性。


字段 5  期望效果 Expected Behavior

1. 仓颉编译出的程序应能在上述 Windows 补丁级别上正常启动并执行 main，
   输出 hello from Cangjie，生成 marker.txt，退出码为 0，
   而不是在运行时初始化阶段以 0xC0000005 崩溃。

2. 希望得到以下任一确认或结论。
   2.1 该问题能否在你们的 Windows 26300.9539 与 KB5124010 环境上复现。
   2.2 是否已知与 ntdll 9539 相关的行为变更会影响运行时初始化。
   2.3 1.1.3 是否有可用修复版本，或 Nightly Builds 中是否已修复，
       若有请告知版本号，我们来验证。
   2.4 官方建议的规避方式。我们目前的规避是卸载 KB5124010，
       但这只对能控制更新的用户有效，不能算通用方案。

3. 另建议：cjc 启动时校验前端与后端 LLVM 工具链版本是否匹配。
   我们在用版本管理器切换 SDK 时遇到过 CANGJIE_HOME 与 PATH 中的 cjc 来自不同 SDK 的情况，
   表现为 LLVM 层崩溃并报 Broken module found，看起来像编译器缺陷，实际只是环境串台。


字段 6  源码 Code

以下为完整可复现源码，可直接粘贴，或保存为 repro.cj。
同一文件也放在仓库 cangjie-repro\repro.cj，可作为附件上传。

import std.fs.*

main(): Int64 {
    File.writeTo("marker.txt", "main-ran".toArray())
    println("hello from Cangjie")
    return 0
}

说明
1. marker.txt 这一行是判断崩溃位置的关键，不要删。只留 println 的话，
   进程崩溃时缓冲区不会 flush，会被误判成别的问题。
2. 本文件不含任何项目依赖，单独编译即可复现。
3. 可复现该问题的完整项目，约 3900 行仓颉，供参考：
   https://github.com/XueDric/open-harmony-club-service
   该项目在故障环境下单测与 HTTP 冒烟测试全部无法运行，卸载更新后全部通过，
   可作为影响面的佐证。
