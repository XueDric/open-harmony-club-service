# 轻舟框架 TLS 支持 · 需求说明

- 版本：v1.0
- 日期：2026-09-11
- 提出方：社团管理工具项目组（客户端 + 服务端）
- 接收方：轻舟（QingZhou）框架团队
- 性质：**增强需求，非缺陷**

---

## 1. 背景与目标

我们基于轻舟开发一个社团内部管理工具，服务端部署在一台有公网 IP 的云服务器上，客户端是鸿蒙 App。

当前轻舟的入口只有明文 HTTP：

```
public func listen(port: UInt16): Unit
public func serve(port: UInt16): ServerHandle
```

`src/` 下没有任何 TLS / 证书相关实现。这导致**登录密码与访问 token 会以明文经过公网**，任何同网络的人抓包即可获得 token，进而操作全部社团数据。

**目标**：让轻舟能直接以 TLS 提供服务，从而不需要在前面架设反向代理。

## 2. 优先级与排期

**明确说明：本需求不阻塞我们的 v1 发布。**

我们的 v1 将采用 **Nginx 反向代理终结 TLS** 的方案先上线，因此**请以正确性为第一优先，不要为了赶工牺牲第 4 节的安全要求**。

TLS 是安全关键组件——**配置错误的 TLS 比没有 TLS 更危险**，因为它会带来虚假的安全感。我们宁可晚拿到，也不要拿到一个"能握手但配错了协议版本"的实现。

目标版本：v1.1 增强。

## 3. 接口形态（建议，最终由你们定）

请遵循框架既有的 `xxx()` / `xxxWith(opts)` 命名约定。

```
// 常用形态：直接给证书与私钥路径
listenTls(port, certPath, keyPath)            -> Unit          // 阻塞，对齐 listen()
serveTls(port, certPath, keyPath)             -> ServerHandle  // 非阻塞，对齐 serve()
serveTlsWith(port, opts: TlsOptions)          -> ServerHandle  // 完全控制

TlsOptions 建议字段：
  certPath      : String            证书链（PEM）
  keyPath       : String            私钥（PEM）
  keyPassword   : Option<String>    私钥口令，未加密时为空
  minVersion    : TlsVersion        默认 TLSv1.2
  maxVersion    : TlsVersion        默认 TLSv1.3
```

**语义要求**：

- `listenTls` / `serveTls` 的**阻塞/非阻塞语义必须与现有的 `listen` / `serve` 完全一致**
- 返回的 `ServerHandle` 必须支持现有的 `shutdown()`（排空在途请求）与 `wait()`
- **现有 `listen` / `serve` 的签名与行为不得有任何改变**（见第 6 节）

## 4. 安全硬要求（逐条可测，必须全部满足）

| # | 要求 | 说明 |
| --- | --- | --- |
| 4.1 | **仅允许 TLS 1.2 与 TLS 1.3** | 必须显式禁用 SSLv2 / SSLv3 / TLS 1.0 / TLS 1.1 |
| 4.2 | **证书链完整加载** | PEM 文件可能含多张证书（叶子 + 中间证书），需按文件顺序全部加载 |
| 4.3 | **私钥格式兼容** | 至少支持 PKCS#8（`BEGIN PRIVATE KEY`）与 PKCS#1（`BEGIN RSA PRIVATE KEY`）两种 PEM |
| 4.4 | **禁止静默降级** ⚠️ | 证书或私钥加载失败时，**必须启动即失败并给出明确错误**。绝不能"TLS 起不来就自动退回明文 HTTP" |
| 4.5 | **私钥绝不进日志** | 任何日志、异常信息、堆栈中都不得出现私钥内容或口令 |
| 4.6 | **证书只读一次** | 证书与私钥在**启动时加载并缓存**，不得每次握手重新读盘（我们要跑在 1~2 核的服务器上） |
| 4.7 | **握手失败不致命** | 客户端使用错误协议/畸形数据连接时，只应导致该连接失败，**不得导致进程崩溃或退出** |

> **4.4 是最重要的一条。** 静默降级是这类功能最常见的实现缺陷，且后果严重：服务看起来"正常启动"，实际全程明文。请务必写测试覆盖它。

## 5. 健壮性要求

1. **优雅关闭覆盖 TLS 连接**：`shutdown()` 必须同样排空 TLS 通道上的在途请求，不能只处理明文通道。
2. **资源释放**：连接关闭、握手失败、进程退出时，TLS 上下文与句柄必须被正确释放；长跑不得泄漏内存或文件描述符。
3. **明确的错误信息**：启动期错误需指明是哪个文件、什么问题（文件不存在 / 权限不足 / 格式错误 / 口令错误），不要只给一个泛化的失败。

## 6. 兼容性要求

1. **不破坏现有 API**：`listen` / `serve` 的签名与行为完全不变。
2. **不破坏现有测试**：当前 109 个单测场景必须继续全绿。
3. **Windows 平台可编译运行**：我们本机与服务器**都是 Windows x64**，需要在 Windows 上编译通过并实际跑通 TLS 握手。
4. **零配置默认安全**：不传 `TlsOptions` 时，默认值必须是安全的一侧（最低 TLS 1.2），不能是"全部允许"。

## 7. 验收标准（我们会按此逐条验证）

| # | 验证方式 | 期望结果 |
| --- | --- | --- |
| 1 | `openssl s_client -connect <host>:<port> -tls1_1` | **握手失败** |
| 2 | `openssl s_client -connect <host>:<port> -tls1_2` | 握手成功 |
| 3 | `openssl s_client -connect <host>:<port> -tls1_3` | 握手成功 |
| 4 | 用自签证书（SAN 为 IP）启动并访问 | 正常握手、正常收发请求 |
| 5 | **证书路径故意写错后启动** | **启动失败并报明确错误**（不得回退明文 —— 对应 4.4） |
| 6 | 私钥口令故意写错后启动 | 启动失败并报明确错误 |
| 7 | `openssl s_client` 用错误协议反复连接 | 进程存活，无崩溃 |
| 8 | 现有 109 个单测场景 | 全绿 |
| 9 | 明文 `listen` / `serve` 回归 | 行为与改动前完全一致 |
| 10 | TLS 通道下调用 `shutdown()` | 在途请求排空后退出 |

## 8. 明确**不要求**的内容（范围边界）

为避免不必要的投入，以下**均不在本次范围内**：

- ❌ 双向认证 / 客户端证书（mTLS）
- ❌ SNI 多证书（我们只有一个 IP，不需要）
- ❌ 证书自动续期 / ACME / Let's Encrypt 集成
- ❌ HTTP/2（我们不需要）
- ❌ OCSP Stapling / CRL 检查
- ❌  TLS 会话票据、0-RTT 等性能特性

**如果你们认为其中某项实现成本极低且顺带能做，也请先不要做**——我们要的是尽快拿到一个正确、可验证的最小实现。

## 9. 环境与依赖

**既有事实**（我们从本机 stdx 静态库中提取确认）：

```
libstdx.net.tls.a       1.2 MB
libstdx.net.tlsFFI.a    0.5 MB   -> dlopen "libcrypto-3-x64.dll" / "libssl-3-x64.dll"
```

即 **stdx 已有 TLS 原语，且依赖 OpenSSL 3**。本次工作主要是把 HTTP server 的入口接入 TLS。

**一个必须注意的连带影响**：

- 目前明文模式下缺 OpenSSL 3，只影响 `crypto` 相关功能（返回 HTTP 500，服务仍能启动）
- 接入 TLS 后，OpenSSL 3 会变成**启动期硬依赖**

因此 4.4 的要求在这里尤为重要：**OpenSSL 3 缺失时必须报明确错误并退出，不能静默降级或崩溃。**

## 10. 框架既有约定（请一并遵守）

- **新增文件放 `src/` 即自动纳入编译**，不需要改构建配置
- **文件头采用五段式注释**（SPDX → 标题 → 版权 → 说明 → 公开 API → 约定/注意），写在 `package` 之后
- **单测双轨**：`src/unit_tests.cj`（`@Test`）+ `src/manual_runner.cj`（手写断言）。含 `@Test` 宏的可执行文件会被 Windows Defender 拦截，日常验证请用 manual runner
- **块注释里绝不能出现 `/*`**：仓颉块注释支持嵌套，会吞到文件末尾
- **项目路径保持纯 ASCII**

> 若 `manual_runner.cj` 里"All N unit-test scenarios PASSED"是写死的字符串，请在补充 TLS 用例时同步更新它，或改为动态计数。

## 11. 我们这边的配合

1. **联调支持**：实现完成后我们会在 Windows 上实测，并把失败细节完整反馈（含 `openssl s_client` 输出与启动日志）

## 附：为什么需要这个（一句话背景）

我们不想在长期架构里多维护一个 Nginx——**如果轻舟自己能提供经过验证的 TLS，整个服务端就保持纯仓颉，运维面也小一圈**。这是我们要这个功能的真实动机，而不是为了赶 v1。
