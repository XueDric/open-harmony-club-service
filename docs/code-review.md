### N-1 `GET /join/{token}` 落地页未转义部门名

**状态**：**已修（2026-09-14）**——`strx.cj` 新增 `htmlEscape()`，`joinPageHtml` 对 title / tip 一律先转义；同时按 N-9 补了 CSP 响应头做纵深防御。冒烟里加了两条会因回退而变红的断言（回退版实测 FAIL，页面里原样出现 `<script>alert(1)</script>`）

**现象**（修复前）：L-2 新增的落地页是本项目**第一处 HTML 输出**，但把部门名直接拼进了 HTML。
部门名只校验非空，因此一个含标签的部门名会被原样输出。

**证据**

- `server/src/h_link.cj` —— `joinPageHtml` 用字符串拼接构造页面，`title` / `tip` 未做任何转义：
  ```cangjie
  func joinPageHtml(title: String, tip: String): String {
      return "<!DOCTYPE html>...<title>${title}</title></head>" +
          "..." + "<h2>${title}</h2><p>${tip}</p>" + ...
  }
  ```
- 调用处把部门名拼进标题：`joinPageHtml("加入「${deptName}」", ...)`
- `server/src/h_dept.cj` —— 部门名只校验 `isBlank`，无字符白名单

**实测**

```
POST /api/v1/depts { name: "<script>alert(1)</script>" }   -> 201（被接受）
POST /api/v1/dept-invite-links { dept_id: <该部门> }        -> 201
GET  /join/{token}                                         -> 200
     页面中原样出现 <script>alert(1)</script>（未转义）
```

**影响：中低** —— 理由要写清楚，避免高估或低估：

- 能设置部门名的只有**会长**（`POST/PATCH /depts` 会长独占），所以这不是外部攻击者可控的注入；
  现实场景是"会长自己的误操作"，或将来某个批量导入功能写入脏数据；
- 该 origin 用 `Authorization: Bearer` 头鉴权、**不使用 Cookie**，浏览器里的脚本拿不到会话令牌，
  因此当前拿不到"接管账号"的收益；
- 但落地页是**公开、未鉴权、与 API 同源**的页面，被注入后可做篡改 / 钓鱼；
  **一旦将来在同源加任何浏览器管理界面，这一处立刻升级为真 XSS。**

**建议修法**

1. 在 `joinPageHtml` 里对 `title` / `tip` 做 HTML 转义（`&` `<` `>` `"` `'` 五个字符），
   或对 `deptName` 先过一层字符白名单（部门名本来就该是中文 / 字母 / 数字 / 少量符号）。
2. 顺带加 N-9 的 CSP —— 即使漏了转义，`default-src 'none'` 也能让注入的脚本不执行。

### N-6 注册口令节流是全局锁，可被用来长期挡住正常注册

**状态**：**已修（2026-09-14）**——按拍板结论实现为**按客户端 IP 计数 + 递增退避**，并**不新增接口**（见文末「实际修法」）。

**现象**（修复前）：M-2 的节流是**全局计数**。原报告把它归因于"轻舟没有可信客户端 IP"——
**这个前提本身是错的**（见下）。实测：连错 10 次后 `429`，**此时正确口令也被挡**。
文档已承认这是取舍，但还没写清它**可以被长期维持**。

**证据**

- `server/src/h_auth.cj` —— 全局计数与锁定：`reg_fail_count` / `reg_fail_first_at` / `reg_fail_until`
- 实测：连续错口令第 11 次出现 `429`；随后用**正确**口令注册 → 同样 `429`
- 计数窗口 15 分钟、锁定 15 分钟 → 攻击者每 15 分钟丢 10 个错口令即可维持封锁

**影响**：招新期是社团唯一大量注册的时段，而攻击者（或一个写错的客户端）能让注册入口
在这段时间内持续返回 `429`。属于**低成本、可持续的可用性干扰**，不涉及数据泄露。

**建议修法**（任选，建议 1 + 3）

1. 改成**递增退避**（首次锁 5 分钟，重复触发翻倍，上限 1 小时）—— 正常用户不会被坑太久，
   攻击者的封锁成本上升；
2. 或把阈值放宽（如 15 分钟 20 次）并只在"口令错误"上计数，减少误伤；
3. 补一条**自救路径**：会长在管理页能看到"注册当前被锁定至 X"，并可一键清除
   （现在只能等 15 分钟，或重启服务）；
4. 无论怎么改，`api-design` §2.3 注 6 要补一句"攻击者可用它持续封锁注册"。

**实际修法（2026-09-14）**

前提先被纠正：**"轻舟没有可信客户端 IP"是错的**。轻舟通过 `ctx.http.request.remoteAddr`
暴露 **TCP 对端地址**（`h_ops.cj` 的 `peerOf` 一直在用，`/admin/shutdown` 的"仅本机"就靠它），
那是传输层事实、客户端伪造不了；可伪造的是 `X-Forwarded-For` **请求头**，而本项目直连部署、不读它。
实测该字段文本为 `IP:端口`（例 `127.0.0.1:14764`）。

据此取「**按 IP + 递增退避**」，并且**不新增接口**：

1. **按 IP 分桶**：`Store.reg_fail` 从三个全局字段改成 `HashMap<IP, RegFail>`；新增
   `clientIpOf(ctx)` 从 `IP:端口` 剥出 IP（IPv6 取 `[...]` 内；无括号时按最后一个冒号切）。
2. **递增退避**：首次锁 5 分钟，同一 IP 每再触发一次翻倍，上限 1 小时。
3. **不再需要"会长自救入口"**：那是为对抗**全局**锁设计的（一锁就锁死所有人）。
   改成按 IP 之后，被锁的只有攻击者自己那个地址、正常用户不受影响，
   于是这个新接口**不必加，接口计数保持 39 / 39**。
4. 节流表加条数上限与过期回收（沿用 `pruneLoginFail` 的写法），防内存随 IP 无限增长。

**已知局限**（同时写进 `api-design` §2.3 注 6）：NAT / 校园网出口下整个社团可能共用一个公网 IP，
那时按 IP 会近似退化成全局锁；取不到对端地址时 key 为空串，同样退化为全局。
两者都比"无条件全局锁"更窄。

**回退实测**：把节流改回不分 IP → 单测 **287 / FAIL 5**（含核心的"另一个 IP 不受影响"）；
把锁定检查摘掉 → 冒烟 **336 / FAIL 2**（"锁定期间正确口令"实际返回 **201**，即锁完全失效）。

### N-7 "本接口不能对自己用"对**会长**不成立

**状态**：**已修（2026-09-14）**——取报告建议的"拦行为"路径，但**没有**在 handler 里写 `if`：约束落进 `perms.cj` 的 `checkAccess`（**动作语义层**），权限判定仍然只有一处。

按拍板结论，实现成一条**通用规则**而不是"只保护本人"的特例：**不可重置与自己同权或更高权的人**。
一次覆盖三种情况：

1. **对自己同权** → 谁都不能重置自己（这就是本条 N-7 的原始问题）；
2. **副会长对副会长同权** → 同权之间不能互相踢下线（**原先可以**，属本次一并堵住）；
3. **会长档位最高**，除自己外无人与之同权 → 仍能重置任何更低档的人（没有过度收紧）。

实现细节：这里**不能复用 `outranks()`** —— 它对 `president` 直接短路返回 `true`，会把"会长重置会长自己"放行，正是本条要拦的那一个；所以直接用 `roleRank(target) >= roleRank(actor)` 比较档位，另加一道"目标 id 就是操作者 id"的兜底（防 `target_role` 被填错）。

"本人改自己密码"的通道不变，仍是 `PUT /auth/password`（会长也一样）；只有"彻底忘记原密码"这个边界仍无自助找回（v1 范围取舍，见 `README.md` 未决事项 #4）。

回退实测：单测 **3 条变红**（279 / 3）、冒烟 **1 条变红**（333 / 1，同权重置实际返回 `200`）

**同日推广（2026-09-14，评审之外的一处主动收紧）**

上面只堵住了"重置密码"。继续推广时发现副会长档在 `roleAllows` 里对
`EditMemberName` / `SetRole` / `DisableMember` 也**只排除会长本人**，于是：

比重置密码更严重（直接改角色/状态）。已把同一条规则推广到这三类动作，
判定仍只在 `checkAccess` 的动作语义层。对自己**不**套用这条（改自己的姓名/角色/启停

回退实测（撤回推广）：单测 **294 / FAIL 3**、冒烟 **340 / FAIL 3** ——
冒烟那三条实际全部返回 **200**，即推广前副会长确实能完成降级、禁用、改名。

**现象**（修复前）：`h_secret.cj` 的注释与 `api-design` §3.5 都写"本接口**不能**对自己用"，

## 附录 B · 方法与一处环境误判说明

**方法**

- 所有"实测"结论都在本机跑过，数字（273 / 325 / 22 / `403` / `429` / 字节偏移 22337 等）均为实测值。
- 复验**不使用被复验方新增的测试作为证据**：先用第一轮报告里我自己的复现请求打一遍真实 HTTP，
  再回头核对他们的新断言是否真的能拦住回退。
- 涉及框架语义的结论（M-5 的中间件顺序、洋葱模型）读了轻舟源码 `compose.cj` / `router.cj` / `timeout.cj`。

**一处环境误判（必须说明，避免后人重踩）**

我最初两次跑 `tests/tls-check.ps1` 都得到 `PASS 3 / FAIL 3`，看起来像 TLS 被改坏了。
实际是本会话沙箱限制导致的**客户端假阴性**：

- `openssl` 每次启动即 `couldn't create signal pipe, Win32 error 5`（连续 5 次 0 成功，
  沙箱禁止 MSYS 程序创建 signal pipe）→ 两条 SAN 文本解析断言必失败，
  "错误 IP 必须失败"那条还会**假通过**（因为错误输出里本来就没有 `: OK`）；
- `curl.exe` 与 .NET `SslStream` 则被 Schannel 挡住（`No credentials are available in the security package`）。

### N-12 `clientIpOf` 对无方括号的裸 IPv6

**状态**：**已按建议处理（2026-09-14）**——在 `h_ops.cj` 的 `clientIpOf` 注释里写明这一退化及其后果（这些请求共用一个桶 → 退化为全局，**不是漏洞**），并注明"真要严谨应先判断有无方括号再决定切法"

`clientIpOf` 先找 `]`（`[::1]:port` 形态）；找不到再按**最后一个冒号**切。
